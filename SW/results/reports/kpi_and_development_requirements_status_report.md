## 1. 개발 요건 및 KPI 목표 (Requirements)

### 1.1 개조 구동부 이상 진단 로직 및 머신러닝/통계 기반 알고리즘 개발 (2.2 섹션 원문)

1. **데이터 전처리 및 필터링 로직 구현**
   * 저상형 개조 구동부의 구조적 특성을 반영하여 수집된 소음 데이터의 프로파일링을 수행한다.
   * 실주행 환경에서 유입되는 타이어 노면 소음, 풍절음 등 복합적인 외부 노이즈를 제거하고 감속기/구동축 특유의 주파수 대역 신호를 분리해 낼 수 있는 디지털 필터링 기법을 적용한다.

2. **특징 추출 및 데이터 융합 설계**
   * 시계열 및 주파수 분석(FFT, STFT 등)을 통해 소음 데이터의 특징점(Feature)을 추출한다.
   * 차속, 모터 RPM, 토크 등 차량의 실시간 주행 CAN 데이터를 동기화하여 이상 판단의 보조 입력 변수 및 가중치 산정 기준으로 융합 활용한다.

3. **경량 이상 진단 모델 개발 및 검증**
   * 발주처가 제공하는 기존 정상/고장 데이터셋(또는 문헌적 임계치)을 활용하여 구동부의 이상 상태를 분류할 수 있는 진단 모델을 개발한다.
   * 제공된 하드웨어의 제한적 리소스를 고려하여, 임계치 기반의 경량화된 룰베이스(Rule-based) 알고리즘을 우선적으로 적용하되 딥러닝(인공지능) 모델을 활용한 모델을 활용하여 탐지 정확도와 연산 속도의 균형을 맞추는 것이 중요하다.

### 1.2 핵심 정량적 목표 KPI (2.5 섹션)
| KPI 평가 항목 | 정량적 목표 | 검증 및 측정 방법 |
| :--- | :---: | :--- |
| **1. 시스템 실시간 구동 안정성** | 연속 2시간 무중단 동작 | 실차 장착 후 연속 주행 시 메모리 누수나 제어기 재부팅 없이 정상 구동되는지 확인 |
| **2. 가상 고장 주입 시 이상 탐지율** | 100% (5회 중 5회 성공) | 사전 정의된 가상 고장 데이터(비정상 주파수 재생) 또는 에러 CAN 신호 주입 시 이상 경고 표출 확인 |
| **3. 이상 판별 및 표출 응답성** | 3초 이내 | 가상 고장 신호 주입 시점부터 운전석 디스플레이 경고 UI 표출까지의 전체 통신/연산 지연 시간 측정 |
| **4. 동적 한계 조건 오탐지 (False Alarm)** | 0건 | 과속방지턱, 요철, 급가감속 등 물리 충격 발생 실차 주행 시 이를 이상으로 오인하여 경고를 표출하지 않는지 확인 |

### 1.3 정상 차량 기반 오탐지(False Alarm) 검증 요건
* **J-turn, 슬라럼, 원선회, 급가감속, 과속방지턱 통과 등 다양한 동적 주행 한계 시험을 수행한다.**
* **급격한 하중 이동이나 노면 충격을 구동부 결함(이상)으로 오인하지 않도록 알고리즘의 변별력을 현장 튜닝하고 미탐/오탐율을 최소화 한다.**

## 2. 지금까지 시도해본 것 (What We Have Tried So Far)

### 2.1 데이터 수집, 정합성 검증 및 동기화 데이터셋 구축
* **32개 오디오 채널 내구/오프셋 전수 실측**:
  - 16개 주행 시나리오에 대한 32개 오디오 파일(Gear-1 16개 + OBD-2 16개)의 실제 수집 시간을 분석하여 정상(Aligned), 유휴 정면 딜레이(Front Delay), 전면 오디오 누락(Missing) 카테고리로 정밀 분류 완료.
* **CAN 타임스탬프 기준 1:1 오디오 동기화**:
  - CAN 타임스탬프 Time 수치 기반 44.1kHz 오디오 샘플 1:1 정밀 슬라이싱 구현 완료.
  - CAN 1개 행(평균 4.0ms) 수집 시간 폭 내에 들어있는 오디오 샘플 개수(평균 175.87개)를 16개 전체 시나리오(294,905개 구간) 전수 실측 검증 완료.
* **출발점 기준 물리적 시간 재교정 및 독립 보조 데이터셋 구축**:
  - 차량 실제 출발 시점(Launch Point)을 기준으로 앞부분 정차 대기 시간을 정밀 절단(Trim)하고, 0.74초 윈도우별 8대 음향 피처가 포함된 독립 보조 데이터셋(`unified_audio_context_dataset_w250.csv`) 구축 완료.

### 2.2 DSP 신호처리 기법 연구 및 C++ 룰 도출
* **힐베르트 변환 포락선(Hilbert Envelope) 분석**:
  - 기어 씹힘 충격파 추출 시 고장 상태 충격파 수치가 정상 대비 **+27.5% ~ +28.9% 대폭 상승**함을 수치 검증 완료.
* **STFT 주파수 전력 스펙트럼 분석**:
  - 고장 시 2.8 kHz 지점의 -30 dB 고장 기본 피크 및 4 ~ 10 kHz 고차 조화파 층상 밴드 관측 완료.
* **C++ 호환 초경량 룰 수식 설계**:
  - 신경망 연산량 0 FLOPs의 C++ 초경량 룰 알고리즘 (`compute_audio_rule_score`) 수식 및 임계값 기준(2.8 kHz > -45 dB 또는 고차 조화파 > -60 dB) 도출 완료.

### 2.3 AI/ML 머신러닝 및 시계열 딥러닝 이상 진단 모델 구축
* **원시 시계열 분류**: XGBoost (Accuracy 79.07%, F1 0.7852) 및 Random Forest (Accuracy 90.90%, F1 0.9087) 모델 평가 완료.
* **윈도우 피처 분류**: 43개 피처 데이터셋 기반 XGBoost (Accuracy 100%) 및 Random Forest (Accuracy 98.90%) 성능 평가 완료.
* **2단계 하이브리드 이상 진단 파이프라인 (2-Step Hybrid Pipeline)**:
  - Step 1 비지도/시계열 (One-Class SVM / PyTorch LSTM) + Step 2 지도 (XGBoost) 결합 모델 구현 완료.
  - 5-Fold CV 결과 **Accuracy 98.22%, F1-Score 0.9826** 성능 달성.

### 2.4 실시간 연산 지연 시간(Latency) 벤치마크
* **43개 전체 피처 연산 속도 정밀 실측**:
  - PC Python: 0.25 ms (4ms CAN 주기의 6.25% 점유)
  - 라즈베리파이 4/5 (C++): 0.45 ms (4ms CAN 주기의 11.25% 점유)
  - Nordic nRF52840 (C++ CMSIS-DSP): **0.33 ms (4ms CAN 주기의 8.25% 점유)**
  - 43개 전체 피처를 계산하더라도 nRF52840 임베디드 보드 기준 4ms 주기의 8.25%만 사용하므로 10% 이내 실시간 처리 조건 충족 확인.

## 3. 해결 방법 및 실차 검증 이행 계획 (Solutions & Action Plan)

### 3.1 KPI 1 (연속 2시간 무중단 동작 & 메모리 누수 0건) 해결 방안
* **메모리 구조**:
  - 데이터를 디스크나 동적 배열에 계속 쌓지 않고, **250개(0.74초) 크기의 고정 링버퍼(Circular Buffer)**를 선입선출(FIFO)로 재사용하여 메모리 증가를 차단.
* **실측 검증 이행 계획**:
  - Python `tracemalloc` 및 C++ `Valgrind` 메모리 프로파일러를 연동하여, **2시간 연속 신호 주입 환경에서 메모리 점유율 변화(0 Byte 증가)를 수치로 측정하고 검증 보고서 작성.**

### 3.2 KPI 2 (가상 고장 주입 이상 탐지율 100%) 해결 방안
* **학습 외 신호(OOD) 검증 시뮬레이터 구축**:
  - 오프라인 데이터셋 외에 **학습에 사용되지 않은 가상 주파수 오디오 신호 및 에러 CAN 메세지를 강제로 주입**하는 범외(Out-of-Distribution) 이상 탐지 테스트베드 구축.
* **탐지율 검증 이행 계획**:
  - 5회 이상 가상 고장 신호 인젝션 시 1단계 룰/비지도 경고 Trigger가 100% 발동하는지 실측 수치 검증.

### 3.3 KPI 3 (이상 판별 및 표출 응답성 3초 이내) 해결 방안
* **End-to-End 파이프라인 지연 시간 측정**:
  - 피처 추출 연산(0.33 ms) 및 모델 추론(1 ms 미만) 외에, **신호 발생부터 CAN 버스 송신 및 디스플레이 UI 경고 팝업까지의 전체 시스템 파이프라인 응답 속도 실측.**
* **통신 지연 최소화**:
  - 경고 메시지를 최우선 우선순위 CAN ID로 디스플레이 제어기에 송신하여 **전체 지연 시간을 0.1초 이내로 유지.**

### 3.4 KPI 4 (동적 주행 한계 시험 및 오탐지 최소화) 현실적 한계 및 정밀 대응 방안

#### 3.4.1 데이터셋 현황 및 현실적 한계 분석
* **데이터 부재 한계**: 현재 보유한 16개 주행 데이터셋에는 과속방지턱, 요철로, 슬라럼, J-Turn 전용 실측 로그가 부재하므로, 순수 데이터 기반 학습만으로는 동적 한계 주행 시의 오탐을 완전히 방어하기 어렵습니다.
* **현실적 대응 방향**: 지속적인 감속기 고장 신호와 일시적인 노면/하중 충격의 물리적 특성 차이를 활용한 **'알고리즘적 시간 필터링 및 동적 마스킹'**을 통해 오탐률을 최소화합니다.

#### 3.4.2 오탐 최소화를 위한 3대 실무 엔지니어링 방어 전략
1. **[시간적 방어] 3초 지속성 디바운싱(Debouncing) 타임 필터**:
   - **물리적 차이**: 과속방지턱/요철/J-Turn 충격은 0.1 ~ 0.5초 이내의 단발성 충격인 반면, 감속기 고장은 영구적이고 지속적인 진동/저항을 유발함.
   - **로직**: 단일 윈도우(0.74초)가 순간적으로 튀더라도 즉시 경보를 울리지 않고, **최근 3초 동안 연속 3회 이상 이상 판정이 지속될 때만 최종 경고를 확정**하여 단발 충격 오탐을 최소화함. (단, 연속 요철로나 비포장도로 주행 시의 잔여 오탐 가능성은 현장 튜닝으로 보완 필요)
2. **[동역학 방어] CAN 조향/가속도 기반 동적 마스킹 (Cross-Sensor Dynamic Masking)**:
   - 조향각 속도(`sas_speed_mean`)나 횡가속도(`lat_accel`)의 변화율이 급증하는 급선회/슬라럼 구간에서는 이상 판단 임계값을 동적으로 일시 상향하거나 판정을 0.5초간 보류함.
3. **[사전 검증] 합성 노면 충격 스트레스 주입 시뮬레이션**:
   - 정상 주행 데이터에 가상의 과속방지턱 펄스(Spike) 및 급가감속 하중 이동 신호를 합성 주입하여, 디바운싱 및 마스킹 로직의 오탐 억제 변별력을 사전에 정량 평가하고 임계값을 현장 튜닝함.

### 3.5 알고리즘 실차 C++ 패키징 및 모터 RPM/토크 신호 확장
* **C++ 라이브러리 패키징**:
  - 파이썬 기반 알고리즘을 실차 탑재용 **Native C++ 모듈 (DLL / Shared Object)**로 재구현 및 메모리 버퍼 연결.
* **CAN 신호 확장**:
  - 실차 수집 CAN 메세지에서 `모터 RPM` 및 `토크` 신호 수신 시, 슬립비 및 차속 정규화 수식에 추가 대입하여 진단 정밀도 보강.
